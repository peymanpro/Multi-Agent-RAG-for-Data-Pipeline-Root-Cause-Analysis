# Releasing

## Release contract

A stable release uses a tag in the form `vMAJOR.MINOR.PATCH`. The tag must exactly match `[project].version` in `pyproject.toml`; the workflow rejects malformed tags and version mismatches before running release steps.

The release workflow is tag-driven. Pushing a version tag starts the following process on the tagged commit:

1. Install the package, development tools, and build tools.
2. Validate the tag against package metadata.
3. Run Ruff, mypy, and the complete offline pytest suite.
4. Generate the deterministic diagnostic benchmark report.
5. Build the source distribution and wheel.
6. Validate distribution metadata with Twine.
7. Create SHA-256 checksums for the distributions and benchmark report.
8. Publish a GitHub Release with generated release notes and attached artifacts.

The workflow does **not** publish to PyPI. Package publication can be added separately after a PyPI project and trusted-publishing identity have been configured.

## Maintainer release procedure

1. Merge the intended changes to `main` only after the pull request checks pass.
2. Update `project.version` in `pyproject.toml` in a reviewed commit.
3. Ensure the CI workflow is green on that exact commit.
4. Create and push an annotated tag that matches the version, for example:

   ```bash
   git switch main
   git pull --ff-only
   git tag -a v0.1.0 -m "Release v0.1.0"
   git push origin v0.1.0
   ```

5. Inspect the Actions run and the published Release page. Do not describe a release as complete until the run succeeds and the assets are present.

Do not tag a commit that does not contain the matching version bump. If validation or packaging fails, fix the source on a new commit, rerun CI, and create a new version tag; avoid moving or force-updating published release tags.

## Attached assets

Each automated GitHub Release includes:

- a Python wheel;
- a source distribution;
- the deterministic diagnostic benchmark report generated by that tagged commit;
- `SHA256SUMS` for the distribution files and report.

Benchmark timing values are observational and may vary by runner. The diagnostic benchmark evaluates the deterministic diagnostics baseline; it does not establish production root-cause accuracy. See [Benchmark Design](benchmark-design.md) for the measurement boundary.
